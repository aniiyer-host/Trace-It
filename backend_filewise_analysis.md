## Root Configuration Files

### .env and .env.test
- **Purpose**: Store environment variables for development and testing environments.
- **Content**: 
  - `.env`: Contains `DATABASE_URL` (pooled connection) and `DIRECT_DATABASE_URL` (direct connection) for Supabase PostgreSQL, plus `PORT` and `NODE_ENV`.
  - `.env.test`: Likely similar to `.env` but configured for a test database (though not examined in detail).
- **Role**: Used by `dotenv` to load configuration into `process.env`. The backend requires two connection strings due to Prisma 7's setup: one for the app (pooled via PgBouncer) and one for migrations (direct).

### Dockerfile
- **Purpose**: Define the container image for the backend service.
- **Content**: (Not examined in detail, but inferred from context) Likely uses a Node.js base image, copies source, installs dependencies, builds TypeScript, and sets the start command.
- **Role**: Enables deployment of the backend in a consistent, isolated environment.

- **Purpose**: Provide setup, development, and troubleshooting instructions for the backend.

### package-lock.json
- **Purpose**: Lock exact versions of dependencies for reproducible builds.
- **Content**: Auto-generated by npm; not to be modified manually.
- **Role**: Guarantees that all developers and CI/CD pipelines use the same dependency versions.

### package.json
- **Purpose**: Define project metadata, dependencies, and scripts.

## Prisma Schema and Migrations

### prisma/schema.prisma
- **Purpose**: Define the database schema (models, enums, relations) for Prisma ORM.
- **Content**: (Not examined in detail) Based on README: uses camelCase field names (no snake_case mapping), defines models like `User`, `Donation`, `Campaign`, etc., likely with relations and indexes.
- **Role**: Single source of truth for database structure; Prisma generates client models and migration SQL from this file.

### prisma/seed.ts
- **Purpose**: Populate the database with initial data for development and testing.
- **Content**: (Not examined in detail) As per README: creates admin, NGO, donors, campaigns, etc. Ran via `prisma db seed`.
- **Role**: Ensures a consistent starting state for developers and test suites.

### prisma/migrations/
- **Purpose**: Store SQL migration scripts for evolving the database schema.
- **Content**: Three migration directories observed:
  1. `20260815122959_init/migration.sql`: Initial schema creation (tables for all models).
  2. `20260815123000_add_triggers_and_functions/migration.sql`: Custom PostgreSQL triggers and functions (e.g., `set_updated_at`, `sync_campaign_raised`, `mark_tokens_redeemed`, `handle_legal_hold`).
  3. `20260818000001_create_blockchain_retry_queue/migration.sql`: Creates the `BlockchainRetryQueue` table for handling failed blockchain transactions.
- **Role**: Migration history; applied in order via `prisma migrate deploy`. The triggers file is critical for automatic timestamp updates and business logic enforcement at the database level.

- **Purpose**: Initialize and export the Prisma client instance.
- **Content**: Uses `prisma.config.ts` (or directly references environment) to create a singleton Prisma client.
- **Role**: Centralized database access point; imported by services to perform queries.

### src/index.ts
- **Purpose**: Entry point of the Express application.
- **Content**:

  - Registers routes (auth, donor, charity, admin, public, webhooks).
  - Implements error handling (404, general error handler).
  - Starts the server on `PORT`.
- **Role**: Bootstraps the API; defines the middleware pipeline and route mounting.

### src/lib/utils.ts
- **Purpose**: Utility functions used across the backend.
- **Content**: (Not examined in detail) Likely includes helpers for formatting, validation, crypto, etc.
- **Role**: Reduces code duplication by centralizing common logic.

### src/middleware/
- **errorHandler.ts**: Central error handling middleware; formats error responses, logs errors, and sends appropriate HTTP status codes.
- **kycCheckMiddleware.ts**: Checks if a user has completed KYC (Know Your Customer) requirements; likely used on donation-related routes.
- **multerMiddleware.ts**: Configures Multer for file uploads (e.g., for receipts or documents); sets storage limits and file types.
- **notFound.ts**: 404 middleware for undefined routes.
- **requestIdMiddleware.ts**: Generates a unique request ID for tracing and logs it.
- **requestLogger.ts**: Logs incoming requests (method, URL, IP, etc.) and outgoing responses.
- **requireAuth.ts**: JWT authentication middleware; verifies token and attaches user to request.
- **requireRole.ts**: Role-based access control middleware; checks if user has required role (e.g., admin, NGO).
- **strictLimiter.ts**: Rate-limiting middleware to prevent abuse (likely using express-rate-limit).

### src/routes/
- **admin.ts**: Admin-only routes (e.g., managing users, NGOs, campaigns, viewing analytics).
- **auth.ts**: Authentication routes (login, register, logout, password reset).
- **charity.ts**: Routes for NGO/charity operations (profile, donation history, etc.).
- **donor.ts**: Routes for donor operations (profile, donation history, etc.).
- **public.ts**: Publicly accessible routes (e.g., campaign listings, donation processing without auth).
- **webhooks/razorpay.ts**: Handles Razorpay payment webhooks (verifies signature, updates donation status).

### src/services/
- **auditLogService.ts**: Logs important actions (e.g., donation created, user updated) to an audit trail.
- **authService.ts**: Handles authentication logic (password hashing, token generation, user validation).
- **blockchainInstance.ts**: Initializes and manages connection to the Solana blockchain (via Anchor/web3.js).
- **blockchainRetryProcessor.ts**: Processes failed blockchain transactions from the `BlockchainRetryQueue` (retries with exponential backoff).
- **blockchainService.ts**: High-level blockchain interactions (record donation on-chain, update status, etc.).
- **documentService.ts**: Manages document uploads/storage (e.g., for KYC or receipts) using AWS S3 or Azure Blob Storage.
- **donationService.ts**: Core business logic for donations (create, update, retrieve, validate).
- **emailService.ts**: Sends emails (e.g., donation receipts, welcome emails) via an email service (likely AWS SES or similar).
- **hashService.ts**: Provides hashing utilities (e.g., for file integrity, password hashing via bcryptjs).
- **receiptService.ts**: Generates donation receipts (PDF or HTML) and stores/delivers them.
- **statusService.ts**: Manages status updates for donations (e.g., pending, processed, failed).

## How It All Works Together

1. **Request Lifecycle**:
   - An HTTP request hits `src/index.ts`.
   - Middleware pipeline processes it: logs request, assigns ID, checks rate limits, parses body, validates auth/role, etc.
   - The request is routed to the appropriate controller in `src/routes/`.
   - The controller delegates to a service in `src/services/` (e.g., `donationService.createDonation`).
   - The service uses the Prisma client (`src/db/prisma.ts`) to interact with the database.
   - For blockchain operations, services call `blockchainService` or `blockchainInstance`.
   - After processing, a response is sent back through middleware (error handling, logging).

2. **Database Layer**:
   - Prisma ORM (via client in `src/db/prisma.ts`) translates TypeScript method calls to SQL.
   - Custom PostgreSQL triggers (from migrations) automatically update `updatedAt` timestamps and enforce business logic (e.g., updating campaign totals when a donation is recorded).

3. **Blockchain Integration**:
   - `blockchainInstance.ts` sets up a connection to Solana devnet/localnet.
   - `blockchainService.ts` uses Anchor to interact with the Trace-it Solana program (record donations, update status).
   - Failed transactions are logged to `BlockchainRetryQueue` table; `blockchainRetryProcessor.ts` retries them.

4. **External Services**:
   - File uploads go to AWS S3 or Azure Blob Storage via `documentService`/`storageService`.
   - Emails are sent via `emailService` (configured with SMTP/API keys).
   - Logging is sent to stdout and optionally Elasticsearch via `winston` and `winston-elasticsearch`.

5. **Testing**:
   - Jest runs tests in `--runInBand` mode to avoid concurrency issues with database.
   - Tests use the test database (seeded via `prisma db seed` in `jest.setup.js` or similar).
   - Trigger tests verify database-level logic works as expected.

This architecture separates concerns: routes handle HTTP, services handle business logic, Prisma handles data access, and middleware handles cross-cutting concerns (auth, logging, etc.).
